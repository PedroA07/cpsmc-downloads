Para o Processamento de Dados

Instalar o servidor

O aplicativo é só a interface — ele nunca fala com o banco direto. Toda leitura e escrita passa pela API, que roda em uma máquina da rede interna junto do PostgreSQL. Este guia monta essa máquina uma única vez; depois disso, instalar o sistema em cada computador é só rodar o instalador.

1

Escolha a máquina

Um computador da rede interna que fique ligado no horário de expediente. Windows ou Linux, 64-bit, com 4 GB de memória e 20 GB livres já atendem o volume da autarquia. Ele precisa de IP fixo ou nome estável na rede — é esse endereço que os aplicativos vão procurar.

2

Instale os pré-requisitos

São quatro programas: Git (para baixar o código), Node.js 20 ou superior, pnpm 10 ou superior e o PostgreSQL 16. O caminho mais curto para o banco é o Docker, que já vem configurado no projeto. Nenhum deles vem instalado por padrão — os comandos abaixo instalam tudo.

Windows

Abra o PowerShell como administrador (botão direito no menu iniciar → Terminal (Admin)) e rode:

winget install --id Git.Git -e
winget install --id OpenJS.NodeJS.LTS -e
winget install --id Docker.DockerDesktop -e

Feche o PowerShell e abra de novo antes de continuar — o Windows só atualiza o PATH em janelas novas, e sem isso os comandos continuam “não reconhecidos” mesmo já instalados. Na janela nova:

npm install -g pnpm

Se aparecer que “a execução de scripts foi desabilitada neste sistema”, é a política padrão do Windows bloqueando o pnpm. Libere para o seu usuário e tente outra vez:

Set-ExecutionPolicy -Scope CurrentUser RemoteSigned

Sem o winget, ou sem permissão de administrador: baixe os instaladores em git-scm.com, nodejs.org (versão LTS) e docker.com. O Node também existe em versão ZIP portátil, que dispensa administrador.

O Docker no Windows precisa do WSL

O Docker Desktop não roda sozinho: quem executa os contêineres é o Subsistema do Windows para Linux. Se ele abrir reclamando “WSL not installed”, instale — ainda no PowerShell como administrador — e reinicie o computador:

wsl --install

Depois do reinício, abra o Docker Desktop e espere aparecer Engine running no rodapé antes de seguir. Se o comando reclamar de virtualização, é preciso habilitar Intel VT-x ou AMD-V na BIOS.

Não dá para usar o WSL nesta máquina? Então pule o Docker e instale o banco direto: winget install --id PostgreSQL.PostgreSQL.16 -e. Anote a senha que o instalador pedir, aponte o DATABASE_URL para ele no passo 4, e no passo 5 use os dois comandos que dispensam o Docker.

Confirme antes de seguir

git --version
node --version
pnpm --version
docker --version

Os quatro têm que responder com um número de versão — o Node precisa ser 20 ou maior, o pnpm 10 ou maior. Se algum disser que não é reconhecido, quase sempre é o terminal antigo: feche e abra outro. E o Docker Desktop precisa estar aberto, não só instalado.

Linux (Debian e Ubuntu)

# Git e utilitários
sudo apt update
sudo apt install -y git curl ca-certificates

# Node.js 22 LTS
curl -fsSL https://deb.nodesource.com/setup_22.x | sudo -E bash -
sudo apt install -y nodejs

# pnpm
sudo npm install -g pnpm

# Docker
curl -fsSL https://get.docker.com | sudo sh
sudo usermod -aG docker $USER

Depois do usermod, saia da sessão e entre de novo — é o que faz o seu usuário poder usar o Docker sem sudo.

Confirme antes de seguir

git --version
node --version
pnpm --version
docker --version

Os quatro têm que responder com um número de versão — o Node precisa ser 20 ou maior, o pnpm 10 ou maior.

Sem Docker também funciona: basta um PostgreSQL 16 acessível, com um banco e um usuário criados para o sistema.

3

Baixe o código da API

O código-fonte fica em repositório privado — peça o acesso ao departamento de Processamento de Dados antes de rodar o comando abaixo:

git clone https://github.com/PedroA07/Sistema-CPSMC.git
cd Sistema-CPSMC
pnpm install

Se o Git pedir usuário e senha, use a sua conta do GitHub com um token de acesso pessoal no lugar da senha — o GitHub não aceita mais a senha da conta pela linha de comando.

Sem Git na máquina? Dá para baixar o ZIP: abra github.com/PedroA07/Sistema-CPSMC logado, clique em Code → Download ZIP, extraia e siga de dentro da pasta extraída. Só perde a facilidade de atualizar depois com git pull.

O pnpm install já gera o cliente do banco — não é preciso rodar mais nada nesta etapa.

4

Configure a API

Copie o modelo e abra o arquivo criado:

:: no Prompt de Comando
copy apps\server\.env.example apps\server\.env
notepad apps\server\.env

No PowerShell os dois comandos também funcionam com barras normais: cp apps/server/.env.example apps/server/.env.

cp apps/server/.env.example apps/server/.env
nano apps/server/.env

O arquivo tem uma linha por campo, no formato CHAVE=valor — sem espaços em volta do = e sem aspas. Linhas começadas por # são comentários e podem ser ignoradas. Boa parte já vem preenchida e não precisa ser tocada; o que você precisa decidir está explicado abaixo, campo a campo.

  • DATABASE_URL

    O endereço do banco, no formato postgresql://usuário:senha@máquina:porta/banco.

    Vai usar o Docker do projeto? Então não mexa — o valor que já veio corresponde ao banco que o passo 5 vai criar.

    Só troque se você tiver um PostgreSQL próprio: use o usuário, a senha e o nome de banco que o seu DBA criou para o sistema.

  • PORT

    A porta em que a API escuta. Deixe 3333. Só mude se essa porta já estiver ocupada por outro serviço na máquina — e, se mudar, use a mesma no passo 7 e no endereço do passo 8.

  • CORS_ORIGENS

    A lista de origens que a API aceita atender. Não mexa — e principalmente não remova o null do final.

    É ele que autoriza o aplicativo instalado: o programa empacotado carrega de file:// e se identifica como origem nula. Sem essa entrada, o login funciona em desenvolvimento e falha no aplicativo instalado, sem mensagem de erro clara.

  • JWT_ACCESS_SECRET JWT_REFRESH_SECRET

    Duas senhas longas e aleatórias que a API usa para assinar as sessões. Não são digitadas por ninguém — você gera e cola.

    Rode o comando abaixo duas vezes e cole cada resultado em um dos campos. Precisam ser diferentes entre si, e diferentes em cada servidor:

node -e "console.log(require('crypto').randomBytes(48).toString('base64url'))"
  • JWT_ACCESS_EXPIRACAO JWT_REFRESH_EXPIRACAO

    Depois do login, a senha não é conferida de novo: a API entrega ao aplicativo um passe, um texto embaralhado que vai junto de cada pedido ao servidor e serve de identificação. São dois passes, com finalidades diferentes.

    O de acesso (15m) é o que acompanha cada clique. O de renovação (7d) fica guardado, não abre nada sozinho e só serve para pedir um passe de acesso novo quando o anterior vence.

    Ninguém redigita a senha a cada 15 minutos: quando o passe de acesso vence, o aplicativo troca por outro sozinho, sem o usuário ver nada. A tela de login só reaparece depois de 7 dias sem usar o sistema, porque cada renovação reinicia essa contagem.

    O que cada prazo controla: 15m é por quanto tempo um passe roubado ainda funcionaria na mão de outra pessoa — por isso é curto, já que ele trafega pela rede o tempo todo. 7d é quanto tempo de inatividade até ter de entrar de novo.

    Deixe como está. Encurtar o de renovação faz o funcionário reentrar à toa; alongar mantém a sessão viva na máquina de quem saiu de férias ou foi desligado. E note que nada disso atrasa um bloqueio: desativar um usuário tem efeito no clique seguinte, porque a API confere o cadastro dele a cada requisição.

  • SEED_ADMIN_LOGIN

    O nome de usuário do primeiro administrador. Deixe admin, a menos que a autarquia use outro padrão de login.

  • SEED_ADMIN_SENHA

    A senha desse primeiro acesso — escolha uma e anote. É com ela que você vai entrar no sistema pela primeira vez.

    Deixando em branco também funciona: o passo 5 sorteia uma senha e a mostra uma única vez no terminal. Se você fechar a janela sem anotar, não há como recuperá-la.

    Depois de entrar e trocar a senha dentro do sistema, apague o valor daqui — ele não serve mais para nada e não deve ficar guardado.

  • TLS_KEY_PATH TLS_CERT_PATH

    São dois arquivos de texto que embaralham o tráfego entre o aplicativo e o servidor e provam que o servidor é quem diz ser. Sem eles, a senha que o funcionário digita atravessa a rede legível.

    A chave privada vai em TLS_KEY_PATH — é o segredo, nunca sai do servidor. O certificado vai em TLS_CERT_PATH — é a parte pública, mostrada a quem se conecta.

    Não sabe qual arquivo é qual? Abra cada um no Bloco de Notas: é texto puro, e a primeira linha entrega. A extensão engana (.pem, .key, .crt, .cer) — o conteúdo é que manda. Um arquivo só, .pfx ou .p12, é o par empacotado junto e precisa ser separado antes.

-----BEGIN PRIVATE KEY-----     a chave       -> TLS_KEY_PATH
-----BEGIN CERTIFICATE-----     o certificado -> TLS_CERT_PATH
  • Onde conseguir o certificado

    Peça a quem cuida da rede. É o caminho certo, e a mensagem pode ser esta: “preciso de um certificado TLS para o servidor servidor.cpsmc.local (IP 192.168.x.x), com a chave privada, em formato PEM”. Se a prefeitura tem autoridade certificadora própria, as máquinas da rede já confiam nela e nenhum aviso aparece.

    Não havendo quem emita, dá para gerar o par você mesmo — trocando o nome e o IP pelos reais:

openssl req -x509 -newkey rsa:2048 -nodes -days 825 \
  -keyout chave.pem -out certificado.pem \
  -subj "/CN=servidor.cpsmc.local" \
  -addext "subjectAltName=DNS:servidor.cpsmc.local,IP:192.168.0.10"

O subjectAltName não é opcional: sem ele o aplicativo recusa a conexão, porque navegadores modernos ignoram o campo CN e olham só esse.

O preço desse caminho é que ninguém assinou por você, então cada máquina precisa ser ensinada a confiar nesse certificado — no Windows, instalando o certificado.pem em Autoridades de Certificação Raiz Confiáveis. Sem isso o aplicativo simplesmente não conecta.

Para testar hoje, deixe os dois campos em branco. A API sobe em HTTP, avisa no log e você segue o guia. Só não vá para produção assim.

Salve e feche. Este arquivo guarda senhas — ele nunca vai para o repositório (o .gitignore já bloqueia) e não deve ser enviado por e-mail ou mensagem.

Para conferir, o resultado fica parecido com isto:

DATABASE_URL=postgresql://usuario:senha@localhost:5432/cpsmc?schema=public
PORT=3333

# o "null" é obrigatório: o app instalado carrega de file://
# e envia Origin: null. Sem ele o login falha só na versão instalada.
CORS_ORIGENS=http://localhost:5174,null

JWT_ACCESS_SECRET=(segredo gerado acima)
JWT_REFRESH_SECRET=(outro segredo, diferente)

# senha do primeiro administrador — troque no primeiro acesso
SEED_ADMIN_LOGIN=admin
SEED_ADMIN_SENHA=(defina uma senha forte)

# TLS: obrigatório em produção, mesmo dentro da rede interna
TLS_KEY_PATH=/caminho/para/chave.pem
TLS_CERT_PATH=/caminho/para/certificado.pem

No Windows, escreva o caminho completo com barras normais — C:/certificados/chave.pem. Barras invertidas dentro do .env são interpretadas como escape e quebram o caminho.

5

Crie o banco e o primeiro usuário

Um comando só: sobe o PostgreSQL, aplica as migrations e cria o administrador.

pnpm preparar

No fim ele imprime o quadro com o login e a senha do administrador. Se você deixou SEED_ADMIN_SENHA em branco, a senha é sorteada e aparece uma única vez — anote antes de fechar o terminal. Rodar o comando de novo não recupera a senha: ele preserva o usuário existente de propósito.

Já tem um PostgreSQL próprio, sem Docker? Então rode só as duas últimas partes:

pnpm --filter @cpsmc/server prisma:migrate:deploy
pnpm --filter @cpsmc/server seed
6

Suba a API

pnpm build
pnpm --filter @cpsmc/server start

Espere a linha API disponível em…. Se ela avisar que o TLS está desativado, é porque os caminhos do certificado ficaram em branco — aceitável para testar, não para produção.

Para a API voltar sozinha depois de um reinício

Registre como serviço do Windows com o NSSM (nssm.cc), que é a forma mais simples de manter um processo Node no ar:

nssm install CPSMC-API "C:\Program Files\nodejs\node.exe" "apps\server\dist\main.js"
nssm set CPSMC-API AppDirectory C:\Sistema-CPSMC
nssm start CPSMC-API

Alternativa sem instalar nada: crie uma tarefa no Agendador de Tarefas com o gatilho “ao iniciar o computador”.

Crie a unidade do systemd em /etc/systemd/system/cpsmc-api.service:

[Unit]
Description=API do Sistema Interno CPSMC
After=network.target docker.service

[Service]
WorkingDirectory=/opt/Sistema-CPSMC
EnvironmentFile=/opt/Sistema-CPSMC/apps/server/.env
ExecStart=/usr/bin/node apps/server/dist/main.js
Restart=always
User=cpsmc

[Install]
WantedBy=multi-user.target

Depois ative e suba:

sudo systemctl daemon-reload
sudo systemctl enable --now cpsmc-api
sudo systemctl status cpsmc-api
7

Libere o acesso na rede

O firewall da máquina precisa aceitar conexões na porta 3333 vindas da rede interna.

netsh advfirewall firewall add rule name="API CPSMC" dir=in action=allow protocol=TCP localport=3333

Rode como administrador. Pelo painel: Firewall do Windows Defender → Regras de Entrada → Nova Regra → Porta → TCP 3333.

sudo ufw allow 3333/tcp
sudo ufw status

Em distribuições que usam firewalld: sudo firewall-cmd --permanent --add-port=3333/tcp seguido de sudo firewall-cmd --reload.

Teste de outro computador antes de seguir — se não responder de fora, nenhum aplicativo vai conseguir entrar:

curl https://servidor.cpsmc.local:3333/api/auth/login

Qualquer resposta serve, inclusive um erro de método: significa que a API está no ar e alcançável.

8

Aponte os aplicativos para o servidor

Em cada máquina com o sistema instalado, abra Ajuda → Abrir pasta de configuração e edite o configuracao.json. A pasta é %APPDATA%\Sistema CPSMC\~/.config/Sistema CPSMC/:

{
  "apiUrl": "https://servidor.cpsmc.local:3333/api"
}

Não precisa reinstalar nada — o endereço é lido quando o aplicativo abre. Em instalações em massa, a variável de ambiente CPSMC_API_URL faz o mesmo e tem prioridade sobre o arquivo.

Feito isso, abra o sistema e entre com o login e a senha do passo 5. A primeira coisa a fazer é trocar a senha em Minha conta.

Antes de colocar em produção

  • TLS ligado. Preencha TLS_KEY_PATH e TLS_CERT_PATH. Sem eles a API sobe em HTTP e as senhas trafegam abertas — mesmo dentro da rede interna.
  • Segredos próprios. Os valores de exemplo do .env servem para testar e não podem ir para produção. Gere um segredo distinto para cada ambiente.
  • Senha do administrador trocada no primeiro acesso, e o .env preenchido nunca versionado.
  • Backup do PostgreSQL agendado. Não é feito pelo sistema — é responsabilidade da infraestrutura, e é o que separa um susto de uma perda.
